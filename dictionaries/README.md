# منهجية الترجمة الهندسية وقواعد إدارة القواميس

**English title:** Scriptable Engineering Specification: Translation Methodology and Dictionary Governance

- **الحالة:** معيار عمل معتمد مبدئياً قبل بدء الترجمة.
- **لغة المصدر:** العربية.
- **لغة الهدف:** الإنجليزية التقنية.
- **نوع الوثيقة:** مواصفة هندسية ومعيار حوكمة تقنية.
- **النطاق:** Scriptable, JavaScript, JavaScriptCore, WebView, TypeScript, Software Engineering, and Technical Governance.

## 1. الهدف

تحويل المواصفات العربية إلى وثيقة إنجليزية تحافظ على المحتوى الهندسي والمعنى المعياري والتفاصيل التقنية، دون اختصار أو حذف أو إعادة تفسير أو تغيير في قوة المتطلبات. لا تعتبر الترجمة ناجحة لمجرد سلامة اللغة الإنجليزية، بل يجب أن تحقق اكتمال نقل المعلومات، وصحة المعنى التقني، والحفاظ على القوة المعيارية، واتساق المصطلحات مع المراجع الرسمية، والمحافظة على المعرفات والبنية والعلاقات والأمثلة والروابط، وعدم إدخال معلومات جديدة باعتبارها جزءاً من المصدر.

## 2. قواعد الترجمة الإلزامية

### 2.1 عدم الحذف

- **MUST NOT** حذف أي جملة أو فقرة أو بند أو ملاحظة أو مثال.
- **MUST NOT** اختصار التكرار الموجود في النص الأصلي لمجرد أن المعنى ورد سابقاً.
- **MUST NOT** دمج بندين مستقلين بطريقة تؤدي إلى فقدان أحد المعنيين.
- **MUST** الحفاظ على جميع القيود والاستثناءات والتحذيرات.
- **MUST** الحفاظ على جميع الروابط والإصدارات والأرقام والمعرّفات.

### 2.2 عدم تغيير المعنى

- **MUST** نقل المعنى التقني المقصود، لا مجرد المقابل الحرفي للكلمات.
- **MUST NOT** تحويل التوصية إلى إلزام أو الإلزام إلى توصية.
- **MUST NOT** تحويل الاحتمال إلى حقيقة مؤكدة أو المفهوم غير المتحقق إلى مفهوم مدعوم.
- **MUST NOT** استبدال مصطلح تقني بمرادف لغوي إذا كان ذلك يغير دلالته.
- **MUST** الحفاظ على القيود والاستثناءات وشروط السياق.

### 2.3 الحفاظ على بنية الوثيقة

يجب الحفاظ على ترتيب الأقسام والعناوين وترقيمها، والجداول وأعمدتها وصفوفها، والقوائم المرتبة وغير المرتبة، والشيفرات والأمثلة، وأسماء واجهات البرمجة، والروابط والإحالات، والتحذيرات والاستثناءات، وحالات دورة الحياة والتسميات المعيارية. لا يجوز إعادة تنظيم الوثيقة أو إعادة كتابة بنيتها بهدف تحسين الأسلوب.

### 2.4 الحفاظ على الشيفرات والمعرّفات

تُحفظ دون ترجمة أسماء التقنيات والواجهات والأصناف والدوال والخصائص والمعاملات وأنواع البيانات ومعرّفات القواعد وحالات دورة الحياة. ومن أمثلتها:

`JavaScript`, `ECMAScript`, `JavaScriptCore`, `Scriptable`, `WebView`, `TypeScript`, `JSContext`, `JSValue`, `JSVirtualMachine`, `JSManagedValue`, `JSExport`, `FileManager`, `Request`, `Keychain`, `Location`, `ListWidget`, `importModule()`, `module.exports`, `Promise`, `Array`, `Object`, `String`, `Boolean`, `undefined`, `null`.

## 3. درجات الإلزام المعياري

| المصطلح | المعنى العربي المعتمد | القوة المعيارية |
|---|---|---|
| MUST | يجب | إلزام |
| MUST NOT | يجب ألا، أو يُحظر | منع إلزامي |
| SHOULD | ينبغي | توصية قوية |
| SHOULD NOT | لا ينبغي | توصية بعدم الفعل |
| MAY | يجوز، أو اختياري | سماح أو اختيار |

القواعد:

1. لا تستبدل MUST بـ SHOULD.
2. لا تستبدل MUST NOT بـ SHOULD NOT.
3. لا تستخدم MAY بمعنى الاحتمال اللغوي العادي عندما يكون المقصود السماح المعياري.
4. لا تضف قوة إلزامية غير موجودة في المصدر ولا تخفف قوة إلزامية موجودة فيه.
5. عند وجود صياغة عربية ملتبسة بين الإلزام والتوصية، تسجل في سجل الاستفسارات ولا يحسم معناها بالتخمين.

هذه المطابقة قاعدة تحريرية لهذه الوثيقة، ولا تعني وحدها إعلان الالتزام الرسمي بجميع متطلبات RFC 2119 أو RFC 8174.

## 4. تقسيم الوثيقة إلى وحدات ترجمة

يتم التقسيم وفق العناوين الأصلية، وليس وفق عدد صفحات عشوائي:

- كل وحدة تشمل قسماً كاملاً أو مجموعة عناوين فرعية قصيرة مترابطة.
- لا يُفصل الجدول عن عنوانه أو الملاحظات التي تشرح محتواه.
- لا يُفصل المثال البرمجي عن الفقرة التي تشرح الغرض منه.
- لا يُنقل بند من موضعه الأصلي إلى قسم آخر.
- لكل وحدة رقم ثابت يطابق موضعها في المصدر.

### سجل الوحدات

| المعرّف | محتوى الوحدة | الحالة |
|---|---|---|
| T-001 | الجزء الأول من المواصفات | لم يبدأ |
| T-002 | الجزء الثاني من المواصفات | لم يبدأ |
| T-003 | الجزء الثالث من المواصفات | لم يبدأ |
| T-004 | الجزء الرابع من المواصفات | لم يبدأ |
| … | يستمر وفق ترتيب المصدر | لم يبدأ |

يُحدّث السجل مع تقدم العمل، ولا يُعتبر الجزء منتهياً حتى اجتياز المراجعة.

## 5. مراحل العمل على كل وحدة

### المرحلة A: تثبيت النص المصدر

1. تحديد بداية الوحدة ونهايتها.
2. حفظ ترتيب الفقرات والبنود.
3. تحديد المصطلحات التقنية الموجودة.
4. تحديد العبارات المعيارية.
5. تحديد أسماء الواجهات البرمجية والشيفرات.
6. تحديد العبارات التي تحتاج إلى تحقق مرجعي.

### المرحلة B: إعداد المصطلحات

1. استخراج المصطلحات الجديدة.
2. البحث عنها في القواميس المعتمدة.
3. التحقق من المقابل الإنجليزي في المرجع المختص.
4. تحديد ما إذا كان المصطلح رسمياً أو اصطلاحاً هندسياً أو تسمية خاصة بالمشروع.
5. إضافة المصطلح الجديد إلى القاموس عند الحاجة.
6. عدم تغيير مصطلح سبق اعتماده دون تسجيل سبب التغيير.

### المرحلة C: الترجمة

- استخدام Technical English واضح ودقيق.
- اعتماد American English بصورة موحدة.
- استخدام المصطلحات الرسمية عندما تكون متاحة.
- عدم ترجمة أسماء واجهات البرمجة.
- عدم إعادة صياغة المتطلبات بطريقة تغير قوتها.
- عدم اختصار التفسيرات والأمثلة.
- المحافظة على المصطلحات المتكررة بصيغة إنجليزية موحدة.
- عدم إدخال شروح إضافية داخل النص المترجم دون تمييزها.

### المرحلة D: المراجعة التقنية

| مجال المصطلح | المرجع الحاكم |
|---|---|
| Scriptable APIs | Scriptable Official Documentation |
| JavaScriptCore | Apple JavaScriptCore Documentation |
| JavaScript Language | ECMAScript Specification |
| TypeScript | TypeScript Official Documentation |
| Apple Frameworks | Apple Developer Documentation |
| مصطلحات المشروع الخاصة | قاموس المشروع والقرارات المعتمدة |
| التحقق التشغيلي | اختبار Scriptable الفعلي على الجهاز المستهدف |

لا يجوز استخدام مرجع JavaScriptCore لإثبات وجود واجهة داخل Scriptable، ولا استخدام تعريف TypeScript لإثبات وجود واجهة وقت التشغيل.

### المرحلة E: مراجعة الأمانة للمصدر

تتم مقارنة النص العربي بالإنجليزي بنداً بنداً للتحقق من انتقال جميع المعلومات والقيود والاستثناءات والأمثلة والأرقام والإصدارات، وبقاء درجة الإلزام والعلاقات المنطقية، وعدم تغير معنى المصطلحات أو إدخال معلومة غير موجودة في المصدر. أي اختلاف غير مبرر يمنع اعتماد الوحدة.

### المرحلة F: الاعتماد

لا تعتمد الوحدة إلا بعد مراجعة اكتمال المحتوى والمعنى والمصطلحات والقوة المعيارية والبنية والتنسيق والروابط والأسماء البرمجية.

حالات الوحدة:

`Not Started → Translating → Technical Review → Fidelity Review → Approved`

إذا ظهرت مشكلة، تستخدم الحالة `Technical Review Required` أو `Translation Query`. ولا تنتقل الوحدة إلى `Approved` قبل معالجة المشكلة.

## 6. سجل الاستفسارات والتعارضات

إذا وجد تعارض بين النص العربي والمرجع الرسمي، فلا يصحح النص بصمت. يسجل الاستفسار بالحقول التالية:

| الحقل | المحتوى |
|---|---|
| Query ID | معرّف ثابت |
| Source Location | موضع العبارة في النص الأصلي |
| Arabic Text | النص العربي كما ورد |
| Proposed English | الترجمة المقترحة |
| Reference | رابط المرجع |
| Evidence | النص أو القسم المرجعي الداعم |
| Issue | وصف التعارض أو الالتباس |
| Status | Open / Resolved |
| Decision | القرار بعد المراجعة |

المرجع يساعد على اختيار المصطلح الصحيح، لكنه لا يمنح المترجم صلاحية تعديل حقيقة أو قرار في الوثيقة الأصلية. أي تصحيح للمحتوى يحتاج قراراً مستقلاً عن الترجمة.

## 7. معايير قبول الوحدة

لا تعتمد أي وحدة إلا عند تحقق جميع الشروط التالية:

- اكتمال جميع الفقرات والبنود.
- عدم وجود حذف أو تلخيص.
- عدم وجود تغيير غير مصرح به في المعنى.
- تطابق أسماء واجهات البرمجة والشيفرات.
- اتساق المصطلحات مع القاموس.
- مطابقة درجات الإلزام.
- الحفاظ على ترتيب المحتوى.
- توثيق الاستفسارات غير المحسومة.
- عدم تقديم مصطلح تقني غير متحقق باعتباره مصطلحاً رسمياً.

## 8. تصنيف المصطلحات

| التصنيف | المعنى |
|---|---|
| Official API Term | مصطلح أو اسم واجهة وارد في التوثيق الرسمي |
| Standards Term | مصطلح وارد في معيار أو مواصفة رسمية |
| Apple Framework Term | مصطلح خاص بوثائق Apple وأطرها |
| TypeScript Term | مصطلح خاص بلغة TypeScript وأدواتها |
| Engineering Term | مصطلح هندسي عام |
| Project-defined Term | تسمية أو مفهوم محدد داخل مواصفات المشروع |
| Unverified Term | مصطلح لم يُحسم مقابله أو مصدره بعد |

لا يجوز وصف المصطلح بأنه `Official` لمجرد شيوعه في المقالات أو المشاريع المجتمعية.

## 9. قواعد اعتماد المصطلح

1. لكل مفهوم مقابل إنجليزي أساسي واحد.
2. تُذكر المرادفات المقبولة عند وجود سبب تقني لاستخدامها.
3. تُحدد الكلمات التي يجب تجنبها عندما تسبب التباساً.
4. تبقى أسماء APIs كما تظهر في التوثيق.
5. لا تُترجم أسماء الأصناف أو الدوال أو الخصائص.
6. لا يُستبدل المصطلح الرسمي بمرادف تسويقي أو لغوي.
7. المصطلحات التي وضعها المشروع تظل موسومة بأنها `Project-defined`.
8. أي تغيير في المصطلح المعتمد يجب تطبيقه باتساق على جميع الوحدات.

## 10. منع التكرار دون فقد المصطلحات الفريدة

1. ملفات هذا المجلد تشكل مجموعة مصطلحية واحدة.
2. لكل مفهوم مدخل أساسي واحد فقط.
3. إذا ورد المدخل نفسه في أكثر من مصدر، يُحتفظ بمدخل واحد وتدمج فيه التعريفات والملاحظات والمراجع الفريدة.
4. لا يُحذف مصطلح فريد لمجرد وجود مصطلح قريب منه.
5. لا تُنشأ مداخل منفصلة لاختلاف الجمع والمفرد أو اختلاف شكلي لا يغير المفهوم. تسجل الصيغ البديلة داخل المدخل الأساسي عند الحاجة.
6. لا تُدمج المصطلحات المتقاربة إذا كانت تشير إلى مفاهيم مختلفة، مثل Compatibility وConformance وCompliance، أو Parameter وArgument.
7. قبل إضافة مصطلح، تُراجع جميع ملفات القواميس بحثاً عن مدخل مطابق أو مقابل معتمد.
8. إذا كان التداخل محتملاً وليس مؤكداً، يسجل للمراجعة بدلاً من الحذف أو الدمج بالتخمين.
9. قاعدة منع التكرار تخص سجلات القواميس، ولا تمنح صلاحية حذف التكرار الموجود في النص المصدر أو الترجمة.

## 11. قائمة ضبط الجودة قبل اعتماد أي ترجمة

### اكتمال المحتوى

- [ ] جميع الفقرات مترجمة.
- [ ] جميع العناوين محفوظة.
- [ ] جميع القوائم محفوظة.
- [ ] جميع الجداول محفوظة.
- [ ] جميع الأمثلة محفوظة.
- [ ] جميع التحذيرات والملاحظات محفوظة.
- [ ] جميع الإحالات والروابط محفوظة.

### الدقة التقنية

- [ ] أسماء APIs مطابقة للتوثيق.
- [ ] أسماء الخصائص والدوال لم تتغير.
- [ ] المصطلحات متوافقة مع القاموس.
- [ ] لم يتم الخلط بين JavaScript وECMAScript.
- [ ] لم يتم الخلط بين JavaScriptCore وScriptable.
- [ ] لم يتم الخلط بين Main Runtime وWebView.
- [ ] لم يتم الخلط بين TypeScript Definitions وRuntime APIs.
- [ ] لم يتم الخلط بين Compatibility وConformance وCompliance.

### الدقة المعيارية

- [ ] MUST محفوظة.
- [ ] MUST NOT محفوظة.
- [ ] SHOULD محفوظة.
- [ ] SHOULD NOT محفوظة.
- [ ] MAY محفوظة.
- [ ] لم تتغير قوة أي متطلب.
- [ ] جميع الاستثناءات والقيود محفوظة.

### الاتساق

- [ ] المصطلح الواحد له مقابل ثابت.
- [ ] لا توجد ترجمات متضاربة للمفهوم نفسه.
- [ ] جميع المصطلحات الجديدة أضيفت إلى القاموس.
- [ ] جميع الاستفسارات مسجلة.
- [ ] لا توجد تصحيحات صامتة للمصدر.

## 12. ملاحظات تحقق يجب الحفاظ عليها

### 12.1 اختلاف إصدار ECMAScript

أثناء التحقق من صفحة ECMAScript الرسمية، ظهر عنوان الصفحة الحية `ECMAScript® 2027 Language Specification`:

https://tc39.es/ecma262/

بينما يحتوي النص العربي المرجعي على إشارة إلى `ECMAScript 2026`. هذا اختلاف زمني يستحق تسجيله للمراجعة عند الوصول إلى القسم المعني. لا يجوز للمترجم تغيير 2026 إلى 2027 بصمت، لأن ذلك سيغير محتوى المصدر. يجب الحفاظ على النص الأصلي في الترجمة وتسجيل المسألة في سجل الاستفسارات إذا كانت تحتاج إلى قرار تحريري.

### 12.2 المصطلحات التوضيحية الخاصة بالمشروع

`Scriptable Main Runtime` و`WebView Runtime` تسميتان توضيحيتان في مواصفات المشروع، وليستا اسمي واجهتين رسميتين معلنتين في وثائق Scriptable. يجب الحفاظ عليهما عند الترجمة مع عدم تقديمهما على أنهما مصطلحان رسميان من الشركة المطورة.

## 13. القرار النهائي

تُعتمد هذه المنهجية والقواميس بوصفها مرجع العمل للترجمة الإنجليزية. لا تبدأ ترجمة أي جزء قبل التحقق من المصطلحات الخاصة به، ولا يعتمد أي جزء قبل اجتياز مراجعة الاكتمال والدقة التقنية والدقة المعيارية.

**القاعدة الحاكمة:** الترجمة تنقل الوثيقة كما هي في محتواها وقوتها المعيارية، والمراجع تضمن صحة المصطلحات التقنية. ولا يملك المترجم صلاحية حذف معلومة أو تصحيح قرار أو تغيير حكم هندسي دون موافقة مستقلة.
