طريقة العمل التي سألتزم بها:

* بناء شجرة قرارات مترابطة.
* طرح جميع القرارات التي أصبحت جاهزة للحسم في جولة واحدة.
* إرفاق توصية واضحة بكل سؤال، بحيث تكون إجابة «نعم» موافقة للتوصية.
* عدم مطالبتك بالبحث عن حقائق يمكن التحقق منها من المصادر.
* عدم كتابة الوثائق أو تنفيذ التغييرات قبل اكتمال الشجرة وتأكيدك أن الفهم مشترك.

2. نقطة البداية المستخلصة من البحث

البحث يثبت ضرورة الفصل بين معيار ECMAScript وواجهات Scriptable وسياقات التشغيل، كما يكشف اختلافات عملية بين بعض التعريفات والسلوك الفعلي، ومخاطر خلط DOM وNode.js مع Main Runtime.

* سلطة الدستور: مطلقة من الناحية المعيارية، ولا تتجاوزه وثيقة أدنى مرتبة.
* النطاق: يشمل المشروع بأكمله.
* حماية GitHub: تشمل ملفات السياسة والكود معاً.

3. الجولة الأولى من القرارات

--------

❓ Q1: خط الأساس لإصدار JavaScript

هل تعتمد ES2015 خط أساس محافظاً، مع السماح بميزات الإصدارات الأحدث فقط بعد إثبات عمل كل ميزة داخل إصدارات Scriptable المستهدفة؟

التوصية: نعم.

* ES2015 هو الأساس المعلن.
* async/await وBigInt وtoSorted() وغيرها لا تُعتمد تلقائياً.
* كل ميزة أحدث تحتاج دليلاً على دعمها في Runtime المستهدف.
* لا يكفي نجاح التحليل النحوي أو فحص TypeScript لإثبات دعم Runtime.

❓ Q2: تصنيف سياقات التشغيل

هل نفرض تصنيفاً صريحاً لكل سكريبت أو وحدة بحسب سياق التشغيل الذي تستهدفه، مع منع نقل افتراضات سياق إلى سياق آخر؟

التوصية: نعم.

أقترح الفصل على الأقل بين:

* Scriptable Main Runtime.
* Widget Runtime.
* Shortcuts.
* Share Sheet.
* WebView.

ويكون لكل سياق واجهاته وقيوده واختباراته وتعريفاته الخاصة. لا يجوز استخدام document أو DOM في Main Runtime لمجرد توفرهما داخل WebView.

❓ Q3: حسم التعارض بين التوثيق والسلوك الفعلي

إذا قالت الوثائق الرسمية شيئاً، وأثبت اختبار قابل لإعادة الإنتاج داخل Scriptable سلوكاً مختلفاً، فما المرجع الذي يحكم قرار التوافق؟

التوصية: اعتماد بروتوكول من مرحلتين:

* تظل الوثائق الرسمية مرجع العقد المعلن للواجهة.
* يُسجل السلوك الفعلي المثبت بوصفه واقع التوافق التشغيلي، ولا يُخفى التعارض أو يُصحح بالتخمين.

ويجب تسجيل إصدار Scriptable وiOS والجهاز والسياق ونتيجة الاختبار والدليل. لا يُعمم سلوك جهاز واحد على جميع الأجهزة.

❓ Q4: حجية تعريفات TypeScript وأدوات التحليل

هل نعتمد تعريفات TypeScript وESLint بوصفها أدوات تحقق مساعدة فقط، مع منعها من أن تكون مصدراً مستقلاً لإثبات وجود Scriptable API؟

التوصية: نعم.

ويترتب على ذلك:

* تثبيت إصدار تعريفات Scriptable ومراجعته.
* عدم إدخال DOM globals إلى Main Runtime.
* عدم إدخال Node globals إلى Main Runtime.
* فصل target عن lib في TypeScript.
* مراجعة تعريفات الواجهات عند ظهور تعارض مع الوثائق أو الاختبار الفعلي.

❓ Q5: سياسة المكتبات والاعتماديات الخارجية

هل تكون المكتبات الخارجية ممنوعة افتراضياً، ولا يسمح بإدخالها إلا بعد تدقيق اعتمادياتها وإثبات توافقها مع Scriptable؟

التوصية: نعم.

يشمل التدقيق:

* الاعتماد على fs أو os أو Node built-ins.
* الاعتماد على DOM أو Browser APIs.
* آليات التحميل الديناميكي والتجميع.
* حجم المكتبة وأثرها على الذاكرة والأداء.
* التوافق مع نظام الوحدات importModule وmodule.exports.
* الترخيص ومصدر الحزمة وإصدارها.

نجاح تثبيت المكتبة أو تجميعها لا يثبت أنها تعمل في Scriptable.

❓ Q6: بوابات الاختبار الإلزامية

هل تجعل جميع طبقات التحقق التالية جزءاً من معيار قبول التغييرات، مع جعل الفحوص الآلية القابلة للتنفيذ بوابات تمنع الدمج عند فشلها؟

التوصية: نعم.

طبقة التحقق	المعيار
Syntax	الصياغة وفق إصدار اللغة المعتمد
Static Analysis	قواعد ESLint والممارسات المحظورة
Type Checking	تعريفات Scriptable المطابقة للسياق
API Compatibility	مراجعة الواجهات المستخدمة
Unit Tests	اختبار الوحدات
Integration Tests	اختبار التكامل
Runtime Verification	اختبار داخل Scriptable الفعلي
Context Verification	اختبار كل سياق مستهدف
Security	فحص الأسرار والاتصالات والمدخلات والاعتماديات

تنبيه: لا يمكن اعتبار Test262 بديلاً عن اختبار واجهات Scriptable، لأنه يختبر معيار ECMAScript وليس Host APIs الخاصة بالتطبيق.

❓ Q7: الاستثناءات الأمنية

هل نعتمد منعاً افتراضياً للعمليات أو الإعدادات عالية المخاطر، ولا يسمح بالاستثناء إلا بموافقة صريحة وتوثيق السبب والنطاق والمدة وآلية المعالجة؟

التوصية: نعم.

يشمل ذلك على الأقل:

* allowInsecureRequest.
* تضمين الأسرار في ملفات المصدر أو السجلات.
* العمليات التي قد تحذف أو تستبدل ملفات.
* الصلاحيات التي تتجاوز الحاجة الفعلية.
* معالجة بيانات خارجية دون تحقق.
* إعادة محاولة عمليات قد يؤدي تكرارها إلى آثار جانبية.

❓ Q8: حدود الأداء والذاكرة

هل نرفض اعتماد أرقام ذاكرة غير مثبتة كحدود رسمية، ونستخدم بدلاً منها قياسات واختبارات موثقة لكل سياق وجهاز مستهدف؟

التوصية: نعم.

مثال ذلك: لا نعتمد 30MB كحد رسمي للـ Widgets لمجرد وروده في مناقشات المجتمع. نميز بين حد موثق من Scriptable، ونتيجة قياس تجريبي، وتوصية احترازية داخل المشروع.

الجولة الثانية: نموذج التوافق والحوكمة

Q9: نطاق التوافق الذي يلتزم به المشروع

هل يجب أن يعلن كل سكريبت أو مكوّن سياقات التشغيل التي يدعمها صراحة، وألا يدّعي توافقاً مع سياق لم يُختبر فيه؟

التوصية: نعم.

أقترح أن تكون السياقات الممكنة:

* التشغيل داخل التطبيق.
* Widget.
* Shortcuts وSiri.
* Share Sheet.
* WebView.
* الإشعارات.
* URL Scheme.

ويكون لكل مكوّن نطاق توافق مستقل. لا يعني دعم Main Runtime تلقائياً دعم Widget أو WebView.

Q10: تصنيف حالة التوافق

ما التصنيف الرسمي الذي تريد اعتماده لكل ميزة أو API؟

التوصية: اعتماد الحالات الخمس التالية:

الحالة	معناها
موثق	موجود في التوثيق الرسمي
مختبر	نجح اختبار فعلي موثق
متوافق	اجتاز جميع متطلبات التوافق المحددة
غير متوافق	ثبت فشل استخدامه في النطاق المحدد
غير متحقق	لا تتوفر أدلة كافية

ويُسمح بوجود أكثر من وصف للميزة إذا اختلفت الإصدارات أو السياقات.

Q11: ترتيب مصادر الحقيقة

عند إعداد قاعدة أو حسم خلاف تقني، هل نعتمد ترتيباً ثابتاً للمصادر؟

التوصية: نعم، وفق هذا الترتيب:

* التوثيق الرسمي لـ Scriptable، لواجهات التطبيق.
* نتائج الاختبار المباشر القابل لإعادة الإنتاج، لإثبات السلوك الفعلي.
* مواصفات ECMAScript، لقواعد اللغة.
* توثيق Apple JavaScriptCore، لفهم المحرك.
* وثائق TypeScript وESLint، لأدوات التطوير.
* مستودعات التعريفات المجتمعية والمناقشات، كأدلة مساعدة لا كمرجع حاكم.

ويجب تسجيل التعارضات بدلاً من إخفائها.

Q12: متطلبات CI والدمج

هل تجعل بوابات GitHub Actions إلزامية قبل دمج التغييرات، مع التفريق بين الاختبارات الآلية واختبارات الجهاز؟

التوصية: نعم.

* الفحوص الآلية: يجب أن تنجح قبل الدمج.
* اختبارات Scriptable الفعلية: يجب تقديم دليلها عند الحاجة إلى إثبات Runtime أو Context Compatibility.
* لا يُقبل ادعاء نجاح اختبار جهاز لم يُنفذ فعلياً.
* لا يحل نجاح CI محل الاختبار على الجهاز.
* فشل بوابة إلزامية يمنع الدمج.

Q13: سلطة الموافقة على الاستثناءات

من يملك صلاحية اعتماد استثناء من معيار Scriptable أو من قاعدة أمنية؟

التوصية: أن تكون الموافقة من مالك السياسة أو الجهة التي تفوضها الوثيقة الدستورية، مع توثيق:

* القاعدة المستثنى منها.
* سبب الاستثناء.
* الملفات أو المكونات المشمولة.
* المخاطر والضوابط التعويضية.
* تاريخ انتهاء الاستثناء أو موعد مراجعته.

ولا يجوز أن يلغي الاستثناء قاعدة دستورية أعلى منه.

Q14: نموذج تقسيم النظام إلى وحدات

هل تعتمد بنية طبقية تفصل منطق الأعمال عن واجهات النظام والتخزين والاتصال وواجهة المستخدم؟

التوصية: نعم.

أقترح النموذج التالي:

Features / Business Logic

وظائف النظام وقواعد العمل

Core

الإعدادات، الثوابت، الأخطاء، التسجيل

Data

التحقق، التحويل، العقود

Services

الشبكة، التخزين، المصادقة

UI

القوائم، الجداول، Widgets

Scriptable Host APIs

واجهات التطبيق وiOS

هذا نموذج منطقي للمسؤوليات، وليس فرضاً لأسماء مجلدات أو ملفات بعينها. ويجب أن يكون اختبار منطق الأعمال ممكناً دون الحاجة إلى تشغيل واجهات iOS كلما أمكن ذلك.

Q15: سجل التوافق المركزي

هل يكون هناك سجل مركزي لكل API وميزة JavaScript مستخدمة في المشروع، بدلاً من الاكتفاء بتعليقات متفرقة داخل الملفات؟

التوصية: نعم.

ويحتوي كل سجل على:

* المعرّف واسم الميزة أو API.
* طبقة الانتماء: ECMAScript أو Scriptable أو WebView أو غيرها.
* المصدر المرجعي.
* إصدار Scriptable وiOS المختبر.
* سياق التشغيل.
* حالة التوافق.
* تاريخ آخر تحقق.
* رابط دليل الاختبار أو مصدر التوثيق.
* القيود والاستثناءات.

Q16: إصدارات Scriptable وiOS المستهدفة

* أقدم إصدار Scriptable مدعوم.
* أقدم إصدار iOS مدعوم.
* الإصدارات المستهدفة للاختبار.
* طريقة التعامل مع الإصدارات التي لم تُختبر؟

Q17: نطاق الأجهزة

هل تشمل مصفوفة التوافق جهاز iPhone فقط، مع تسجيل اختلافات الجهاز عند تأثيرها في الواجهات أو الأداء أو سياقات التشغيل؟

التوصية: نعم. ولا نعمم نتائج جهاز على جهاز آخر دون دليل.

Q18: متطلبات إثبات التشغيل الفعلي

هل نلزم بإثبات Runtime داخل Scriptable لكل واجهة جديدة أو متغيرة أو مشكوك في توافقها، بدلاً من اشتراط إعادة اختبار كل واجهة ثابتة في كل تغيير؟

التوصية: نعم. الاختبار يتناسب مع مستوى المخاطر والتغيير، مع بقاء سجل الأدلة قابلاً للمراجعة.

Q19: التوافق الخلفي وإيقاف الواجهات

* توثيق سبب التغيير.
* تحديد المتأثرين.
* تحديد البديل عند وجوده.
* إعلان فترة انتقالية مناسبة.
* تحديث سجل التوافق والاختبارات؟

التوصية: نعم.

Q20: تعريف التغيير الكاسر (Breaking Change)

هل نعرّف التغيير الكاسر بأنه أي تغيير يؤدي إلى تعطيل سكريبت قائم، أو تغيير عقد API أو مخرجاته أو آثاره الجانبية أو متطلبات تشغيله بصورة غير متوافقة؟

التوصية: نعم. ويجب أن يخضع التغيير الكاسر لمراجعة واعتماد مستقلين قبل الدمج.

Q21: درجات الإنفاذ

هل نصنف قواعد الدستور إلى ثلاث درجات؟

الدرجة	معناها
BLOCK	مخالفة تمنع الدمج أو الإصدار
WARN	تحذير يتطلب مراجعة وتوثيقاً
GUIDE	إرشاد موصى به لا يمنع التنفيذ

التوصية: نعم. مع منع تحويل قاعدة إلزامية إلى تحذير لمجرد صعوبة تطبيقها.

Q22: مسؤولية المراجعة والاعتماد

هل نفرّق بين:

* مؤلف التغيير.
* مراجع التغيير.
* صاحب صلاحية اعتماد الاستثناء.
* مسؤول تحديث الدستور وسجل التوافق.

التوصية: نعم. لا أفترض وجود فريق أو مراجعين متعددين؛ نحدد توزيع المسؤوليات وفق واقع المشروع.

Q23: حفظ أدلة التوافق

هل نعتمد سجلاً مركزياً للأدلة يتضمن لكل اختبار: المعرّف، والواجهة، والإصدار، والجهاز، وسياق التشغيل، وخطوات إعادة الإنتاج، والنتيجة، وتاريخ الاختبار، ومرجع الدليل؟

التوصية: نعم. ويجب أن تكون الأدلة قابلة للتتبع إلى القواعد والقرارات التي تثبتها.

Q24: لغة الإلزام المعيارية

هل نعتمد مصطلحات معيارية ثابتة لتحديد قوة كل حكم؟

* MUST: إلزام مطلق ضمن نطاق القاعدة.
* MUST NOT: حظر.
* SHOULD: توصية قوية، ويجوز الخروج عنها بمبرر.
* SHOULD NOT: ممارسة غير موصى بها.
* MAY: خيار مسموح.

التوصية: نعم. مع توثيق معنى كل مصطلح ومنع استخدام الكلمات بصورة متبادلة أو غامضة.

Q25: البنية الإلزامية لكل قاعدة

* معرّف ثابت وفريد.
* عنوان مختصر.
* نص الحكم المعياري.
* النطاق وسياقات التطبيق.
* مستوى الشدة والإنفاذ.
* المبرر الفني.
* المصدر المرجعي.
* طريقة التحقق والاختبار.
* شروط الاستثناء.
* المسؤول عن المراجعة.

التوصية: نعم. ويمكن إضافة حقول أخرى عندما تتطلب طبيعة القاعدة ذلك.

التوصية: نعم. ويجب أن يظل الدستور الأعلى سلطة، حتى عند وجود قاعدة أكثر تخصصاً.

Q27: نطاق تطبيق القواعد

أقترح أن يشمل النطاق:

* Scripts وModules.
* إعدادات المشروع.
* الاختبارات.
* أدوات التطوير وCI.
* الاعتماديات.
* الوثائق والأمثلة.
* ملفات إعداد TypeScript وESLint.

التوصية: نعم. مع تحديد القواعد التي لا تنطبق على نوع معين من الملفات بدلاً من افتراض انطباقها جميعاً.

Q28: صلاحية أدلة التوافق بمرور الوقت

هل نعتبر دليل التوافق صالحاً ضمن الإصدارات والسياقات التي اختُبر فيها فقط، ونعيد التحقق عند حدوث تغيير مؤثر؟

أمثلة التغيير المؤثر:

* تحديث Scriptable أو iOS.
* تغيير API مستخدم.
* تغيير سياق التشغيل.
* تحديث مكتبة أو اعتماد خارجي.
* ظهور بلاغ موثوق عن اختلاف السلوك.

التوصية: نعم. ولا نمدد صلاحية دليل قديم إلى بيئة جديدة دون تحقق.

Q29: دورة حياة الاستثناءات

هل نعتمد دورة حياة موحدة للاستثناء:

Proposed → Reviewed → Approved → Active → Expired/Revoked

بحيث لا يصبح الاستثناء نافذاً بمجرد اقتراحه، ولا يستمر بعد انتهاء صلاحيته دون مراجعة وتجديد صريح؟

التوصية: نعم. ويُسجل تاريخ الموافقة والانتهاء والجهة المعتمدة.

Q30: إصدارات الدستور والتغييرات المعيارية

هل نعتمد نظام إصدار للدستور يميز بين:

* Major: تغيير كاسر في القواعد أو نموذج الحوكمة.
* Minor: إضافة قواعد أو متطلبات جديدة متوافقة مع النموذج الحالي.
* Patch: تصحيح توضيحي أو إصلاح لا يغير المعنى المعياري.

التوصية: نعم. مع سجل تغييرات يوضح ما تغير، ولماذا، وأثره على القواعد السابقة.

الاعتماد: أجب بـ«نعم للجميع» أو حدد أرقام القرارات التي تريد تعديلها. لن أنتقل إلى إنشاء الوثائق قبل إغلاق هذه القرارات ومراجعة نموذج المجال كاملاً معك.

الاجابة نعم للجميع

-------

الجولة الخامسة: ضبط نموذج المجال والمصطلحات

هذه الجولة مهمة لأن بعض المصطلحات التي ظهرت في القرارات السابقة متداخلة، وقد يؤدي عدم الفصل بينها إلى قواعد متناقضة. سنحدد الآن وحدات النموذج وعلاقاتها.

Q31: وحدة إثبات التوافق

هل نعتمد أن التوافق لا يُنسب إلى اسم API وحده، بل إلى تركيبة محددة من العناصر؟

* المكوّن أو السكريبت الذي يستخدم الواجهة.
* واجهة Scriptable أو ميزة JavaScript المستخدمة.
* إصدار Scriptable.
* إصدار iOS.
* الجهاز.
* سياق التشغيل.
* نتيجة الاختبار والدليل.

التوصية: نعم. فنجاح API في Widget مثلاً لا يثبت نجاحه في Main Runtime.

Q32: التمييز بين Script وModule وLibrary

هل نعتمد المصطلحات التالية كمفاهيم منفصلة؟

المصطلح	المعنى المقترح
Script	وحدة قابلة للتشغيل مباشرة من Scriptable
Module	وحدة برمجية تُستورد وتُستخدم من وحدات أخرى
Library	مجموعة وظائف أو وحدات قابلة لإعادة الاستخدام
Dependency	مكتبة أو وحدة يعتمد عليها مكوّن آخر

التوصية: نعم. ولا نستخدم هذه المصطلحات بالتبادل.

Q33: التمييز بين Runtime وExecution Context

هل نفصل بين:

* Runtime: البيئة التي تنفذ JavaScript وتوفر واجهاتها.
* Execution Context: الطريقة أو الحالة التي يُشغّل فيها السكريبت، مثل التطبيق أو Widget أو Share Sheet.
* Host API: الواجهة التي يوفرها Scriptable أو النظام للسكريبت.

التوصية: نعم. هذا يمنع الخلط بين قدرات محرك JavaScript وقدرات التطبيق المضيف.

Q34: طبيعة حالات التوافق الخمس

في Q10 اعتمدنا الحالات: موثق، مختبر، متوافق، غير متوافق، غير متحقق.

لكن هذه الأوصاف ليست بالضرورة متنافية؛ فقد تكون الواجهة موثقة ومختبرة ومتوافقة في الوقت نفسه.

هل نعتمدها بوصفها أبعاداً مستقلة للأدلة والتقييم، لا حالات متتابعة يجب أن تكون إحداها فقط نشطة؟

التوصية: نعم. ويكون لكل بُعد تعريف وشروط إثبات مستقلة.

Q35: الفرق بين عدم التوافق وعدم التحقق

هل نعتمد هذا الفصل الدقيق؟

* غير متوافق: يوجد دليل على فشل الواجهة في نطاق محدد.
* غير متحقق: لا توجد أدلة كافية للحكم.
* غير مدعوم: قرار حوكمة يمنع استخدام الواجهة في المشروع، حتى لو كانت تعمل تقنياً.

التوصية: نعم. فالحظر التنظيمي ليس دليلاً على الفشل التقني.

Q36: مصدر الحقيقة ومصدر الإثبات

هل نفصل بين مفهومين؟

* المصدر المرجعي: يشرح العقد أو السلوك المتوقع، مثل وثائق Scriptable الرسمية.
* مصدر الإثبات: يثبت ما حدث فعلياً، مثل اختبار قابل لإعادة الإنتاج أو تقرير CI.

التوصية: نعم. قد يشرح مصدرٌ ما يجب أن يحدث، بينما يثبت اختبارٌ ما حدث بالفعل. ولا يحل أحدهما محل الآخر.

Q37: العلاقة بين القاعدة والاستثناء والنتيجة

هل نعتمد نموذجاً واضحاً يربط:

Policy Rule → Scope → Enforcement → Exception → Evidence → Decision

أي أن كل مخالفة ترتبط بقاعدة ونطاق، ثم تحدد درجة الإنفاذ، والاستثناء إن وجد، والدليل، والقرار النهائي؟

التوصية: نعم. ويمنع هذا وجود استثناءات غير مرتبطة بقاعدة أو قرارات لا يمكن تتبع أسبابها.

طريقة الاعتماد: يمكنك الرد بـ«نعم للجميع»، أو تحديد أي سؤال تريد تعديله.

---------

Q38: دقة سجل التوافق

هل يكون لكل تقييم توافق سجل مستقل لكل تركيبة من API وإصدار Scriptable وإصدار iOS والجهاز وسياق التشغيل، بدلاً من سجل عام للواجهة؟

التوصية: نعم، مع السماح بإعادة استخدام الأدلة بين التركيبات المتطابقة فقط عندما يكون ذلك مبرراً وموثقاً.

Q39: أنواع الأدلة

هل نصنف الأدلة إلى فئات منفصلة؟

* توثيق رسمي.
* اختبار Runtime مباشر.
* اختبار آلي في CI.
* اختبار TypeScript أو Static Analysis.
* بلاغ أو تقرير مجتمعي.
* استنتاج هندسي لم يُختبر بعد.

التوصية: نعم. ولا يُعامل الاستنتاج الهندسي أو البلاغ المجتمعي على أنه اختبار ناجح.

Q40: متطلبات إعادة إنتاج الاختبار

هل يجب أن يحتوي كل دليل اختبار فعلي على خطوات إعادة الإنتاج، والمدخلات، والنتيجة المتوقعة، والنتيجة الفعلية، وبيئة الاختبار؟

التوصية: نعم. ويُرفق سجل أو صورة أو ملف نتيجة عند توفره.

Q41: التعامل مع الأدلة المتعارضة

إذا نجح اختبار وفشل آخر للواجهة نفسها، هل نحتفظ بالدليلين ونحدد الاختلافات في البيئة والإصدار والسياق قبل إصدار حكم التوافق؟

التوصية: نعم. يمنع حذف الدليل المخالف لمجرد أنه لا يوافق النتيجة المرغوبة.

Q42: إعادة التحقق عند تقادم الأدلة

هل نميز بين:

* دليل صالح لبيئته المحددة.
* دليل يحتاج إلى إعادة تحقق بسبب تغير البيئة.
* دليل متجاوز أو لم يعد صالحاً للاستدلال على الإصدار الحالي.

التوصية: نعم. ولا يعني تقادم الدليل أن الواجهة أصبحت غير متوافقة، بل أن الحكم الحالي يحتاج إلى دليل مناسب.

Q43: تقييم مخاطر التوافق

هل نحدد مستوى مخاطر لكل واجهة أو اعتماد، وفق أثر الفشل واحتماله ومدى انتشار استخدامه؟

التوصية: نعم. ويُستخدم المستوى لتحديد عمق الاختبار وأولوية المراجعة، لا لتجاوز المتطلبات الإلزامية.

Q44: قبول ادعاء التوافق

هل لا يُسمح بوصف مكوّن بأنه «متوافق» إلا إذا استوفى جميع متطلبات التوافق المحددة لنطاقه، وكانت الأدلة المطلوبة متاحة وحديثة بما يكفي؟

التوصية: نعم. ويجب أن يكون الادعاء محدداً بالنطاق، لا عاماً أو مطلقاً.

أجب بـ«نعم للجميع» أو حدد أرقام القرارات التي تريد تعديلها. بعد هذه الجولة سأراجع نموذج المجال كاملاً، وأعرض عليك خريطة المفاهيم والعلاقات والتعاريف للتأكد من أن فهمنا مشترك قبل الانتقال إلى صياغة الوثائق.

الاجابة / نعم للجميع

وفقاً للقرارات التي اعتمدتها، هذه خريطة نموذج المجال المقترح. الغرض منها التأكد من أن المفاهيم والعلاقات تعكس فهمك قبل الانتقال إلى صياغة الدستور والوثائق.

1. خريطة المفاهيم والعلاقات

Governance Constitution

الدستور، السلطة المعيارية العليا للمشروع

Policy Rules

القواعد ومعرّفاتها وأحكامها ونطاقاتها

Governance Model

الأولويات والإنفاذ والاستثناءات

Project Components

Scripts

Modules

Libraries

Dependencies

Compatibility Assessment

تقييم التوافق لكل تركيبة محددة من:

* المكوّن والواجهة المستخدمة.
* إصدار Scriptable وiOS.
* الجهاز وسياق التشغيل.
* نتيجة الاختبار والدليل.

Evidence

مصادر مرجعية واختبارات وأدلة فعلية

Decision

قرار التوافق والإنفاذ والاستثناء

هذه خريطة مفاهيمية، وليست اقتراحاً نهائياً لأسماء الملفات أو المجلدات.

2. التعريفات الأساسية

المفهوم	التعريف المعتمد في النموذج
Constitution	المرجع المعياري الأعلى للمشروع
Policy Rule	حكم معياري له معرّف ونطاق وشروط إنفاذ
Script	وحدة قابلة للتشغيل مباشرة من Scriptable
Module	وحدة تُستورد وتستخدمها وحدات أخرى
Library	مجموعة وظائف أو وحدات قابلة لإعادة الاستخدام
Dependency	مكوّن يعتمد عليه مكوّن آخر
Runtime	البيئة التي تنفذ JavaScript وتوفر واجهاتها
Execution Context	سياق تشغيل السكريبت
Host API	واجهة يوفرها Scriptable أو النظام
Compatibility	صلاحية استخدام ميزة ضمن تركيبة بيئية محددة
Evidence	مادة تثبت التوثيق أو السلوك أو نتيجة الاختبار
Exception	موافقة محددة على الخروج عن قاعدة
Decision	النتيجة الرسمية المبنية على القاعدة والأدلة

3. نموذج التوافق

التوافق ليس خاصية مطلقة للـ API. بل تقييم مرتبط بنطاق محدد.

Compatibility Record

كل سجل يصف نتيجة توافق ضمن بيئة محددة

* Component: المكوّن المستخدم.
* API / Feature: الواجهة أو الميزة المستخدمة.
* Scriptable Version: إصدار التطبيق.
* iOS Version: إصدار النظام.
* Device: الجهاز.
* Execution Context: سياق التشغيل.
* Evidence References: أدلة الإثبات.
* Assessment: نتيجة التقييم.
* Last Verified: تاريخ آخر تحقق.
* Risk Level: مستوى المخاطر.

تمييز مهم: أوصاف «موثق» و«مختبر» و«متوافق» و«غير متوافق» و«غير متحقق» أبعاد تقييم مستقلة، وليست حالات متنافية. أما «غير مدعوم» فهو قرار حوكمة مستقل عن التوافق التقني.

4. دورة تقييم التوافق

* تحديد النطاق
    تحديد المكوّن والواجهة والإصدارات والجهاز وسياق التشغيل.
* جمع الأدلة
    التوثيق الرسمي، واختبارات Runtime وCI والتحليل الساكن، والمصادر المجتمعية.
* تقييم الأدلة
    فحص قابلية إعادة الإنتاج، وحداثة الدليل، والتعارضات والاختلافات البيئية.
* إصدار الحكم
    متوافق أو غير متوافق أو غير متحقق ضمن النطاق المحدد، مع تحديد حالة التوثيق والاختبار.
* تحديد المخاطر والإنفاذ
    تطبيق مستوى المخاطر ومتطلبات الاختبار والقاعدة التنظيمية ذات الصلة.
* المراجعة الدورية
    إعادة التحقق عند تغير الإصدارات أو الواجهات أو السياقات أو الاعتماديات.

5. نموذج القاعدة والاستثناء والقرار

العلاقة التي اعتمدتها في Q37 تصبح:

Policy Rule

Scope

Enforcement

Exception (if applicable)

Evidence

Decision

الاستثناء لا يلغي القاعدة، بل يجيز خروجاً محدوداً عنها وفق موافقة موثقة ومدة محددة وضوابط تعويضية.

6. ما الذي لم يُحسم بعد؟

القرارات الـ47 حسمت المبادئ والنموذج العام، لكنها لا تحدد بعد بعض القيم التشغيلية التي لا يصح اختلاقها، ومنها:

* أقدم إصدار Scriptable وiOS مدعوم.
* الأجهزة الفعلية التي ستُستخدم للاختبار.
* المسؤولون الفعليون عن المراجعة والاعتماد.
* فترات صلاحية الاستثناءات ومواعيد مراجعة الأدلة.
* أدوات CI والفحوص التي يمكن تشغيلها فعلياً.
* كيفية تمثيل السجل في ملفات المشروع.

هذه ليست تناقضات في القرارات، بل تفاصيل تنفيذية تنتظر التحديد.

بوابة اعتماد نموذج المجال

قبل صياغة أي وثيقة، أحتاج تأكيدك أن الخريطة والتعريفات والعلاقات تمثل فهمك المقصود.

هل تعتمد نموذج المجال المعروض؟

نعم، أعتمد النموذج كاملاً وننتقل إلى مرحلة صياغة الوثائق.

أعتمده مع تعديلات أذكرها أدناه.

لا، أريد إعادة بناء النموذج قبل اعتماده.

الجولة السابعة: القرارات التشغيلية المتبقية

Q45: سياسة تحديد الإصدارات المدعومة

هل نعتمد سياسة دعم معلنة تحدد أقدم إصدار Scriptable وiOS مدعوم، مع السماح بتغيير هذه الحدود بإصدار موثق من الدستور؟

التوصية: نعم. ونحدد أرقام الإصدارات الفعلية لاحقاً بناءً على بيئة الاستخدام المستهدفة، لا بالتخمين.

Q46: نطاق الأجهزة المستهدفة

هل نعتمد قائمة أجهزة مستهدفة رسمياً للاختبار، ونميز بين الأجهزة المدعومة والأجهزة التي لم تُختبر؟

التوصية: نعم. ويشمل ذلك تحديد ما إذا كان iPad ضمن نطاق الدعم، وعدم افتراض تطابقه مع iPhone.

Q47: توزيع مسؤوليات الحوكمة

هل نعتمد فصل الصلاحيات حتى لو كان شخص واحد يؤدي أكثر من دور؟

* مالك الدستور.
* مؤلف التغيير.
* المراجع.
* معتمد الاستثناء.
* مسؤول سجل التوافق.

التوصية: نعم. فصل الأدوار مفاهيمي، ولا يشترط وجود خمسة أشخاص مختلفين.

Q48: صلاحية الأدلة زمنياً

هل نعتمد مبدأ انتهاء صلاحية الحكم التشغيلي عند تغير بيئته، مع مراجعة دورية للأدلة عالية المخاطر، بدلاً من فرض مدة موحدة على جميع الأدلة؟

التوصية: نعم. بعض الأدلة تحتاج إعادة تحقق عند تحديث Scriptable أو iOS، بينما أدلة أخرى قد تظل صالحة ضمن نطاقها الأصلي.

Q49: نموذج تقييم المخاطر

هل نعتمد تقييم المخاطر وفق ثلاثة محاور:

* احتمال حدوث الفشل.
* شدة أثر الفشل.
* صعوبة اكتشاف الفشل قبل وصوله إلى المستخدم.

التوصية: نعم. وتُستخدم النتيجة لتحديد أولوية الاختبار والمراجعة، ولا تسمح بتجاوز قاعدة إلزامية.

Q50: المدة الافتراضية للاستثناءات

هل يجب أن يكون لكل استثناء تاريخ انتهاء إلزامي، وألا يسمح باستثناء مفتوح المدة؟

التوصية: نعم. ويُحدد تاريخ الانتهاء وفق مستوى المخاطر، مع تجديد صريح ومراجعة جديدة.

Q51: آلية التعامل مع المخالفات

هل نعتمد مساراً موحداً للمخالفة:

Detected → Classified → Assigned → Remediated / Exception Requested → Verified → Closed

التوصية: نعم. ويجب أن يكون لكل مخالفة مسؤول ونتيجة قابلة للتتبع.

Q52: بوابات التحقق المستمرة

هل نعتمد أن CI لا يكتفي بالفحص عند Pull Request، بل يعيد تشغيل الفحوص المناسبة عند تحديث الاعتماديات أو أدوات التطوير أو قواعد الحوكمة؟

التوصية: نعم. مع عدم ادعاء أن CI يستطيع إثبات توافق Runtime على جهاز فعلي دون تنفيذ اختبار الجهاز.

أجب بـ«نعم للجميع» أو حدد أرقام الأسئلة التي تريد تعديلها.

---------

الجولة السابعة: القرارات التشغيلية المتبقية

Q45: سياسة تحديد الإصدارات المدعومة

هل نعتمد سياسة دعم معلنة تحدد أقدم إصدار Scriptable وiOS مدعوم، مع السماح بتغيير هذه الحدود بإصدار موثق من الدستور؟

التوصية: نعم. ونحدد أرقام الإصدارات الفعلية لاحقاً بناءً على بيئة الاستخدام المستهدفة، لا بالتخمين.

Q46: نطاق الأجهزة المستهدفة

هل نعتمد قائمة أجهزة مستهدفة رسمياً للاختبار، ونميز بين الأجهزة المدعومة والأجهزة التي لم تُختبر؟

التوصية: نعم. ويشمل ذلك تحديد ما إذا كان iPad ضمن نطاق الدعم، وعدم افتراض تطابقه مع iPhone.

Q47: توزيع مسؤوليات الحوكمة

هل نعتمد فصل الصلاحيات حتى لو كان شخص واحد يؤدي أكثر من دور؟

* مالك الدستور.
* مؤلف التغيير.
* المراجع.
* معتمد الاستثناء.
* مسؤول سجل التوافق.

التوصية: نعم. فصل الأدوار مفاهيمي، ولا يشترط وجود خمسة أشخاص مختلفين.

Q48: صلاحية الأدلة زمنياً

هل نعتمد مبدأ انتهاء صلاحية الحكم التشغيلي عند تغير بيئته، مع مراجعة دورية للأدلة عالية المخاطر، بدلاً من فرض مدة موحدة على جميع الأدلة؟

التوصية: نعم. بعض الأدلة تحتاج إعادة تحقق عند تحديث Scriptable أو iOS، بينما أدلة أخرى قد تظل صالحة ضمن نطاقها الأصلي.

Q49: نموذج تقييم المخاطر

هل نعتمد تقييم المخاطر وفق ثلاثة محاور:

* احتمال حدوث الفشل.
* شدة أثر الفشل.
* صعوبة اكتشاف الفشل قبل وصوله إلى المستخدم.

التوصية: نعم. وتُستخدم النتيجة لتحديد أولوية الاختبار والمراجعة، ولا تسمح بتجاوز قاعدة إلزامية.

Q50: المدة الافتراضية للاستثناءات

هل يجب أن يكون لكل استثناء تاريخ انتهاء إلزامي، وألا يسمح باستثناء مفتوح المدة؟

التوصية: نعم. ويُحدد تاريخ الانتهاء وفق مستوى المخاطر، مع تجديد صريح ومراجعة جديدة.

Q51: آلية التعامل مع المخالفات

هل نعتمد مساراً موحداً للمخالفة:

Detected → Classified → Assigned → Remediated / Exception Requested → Verified → Closed

التوصية: نعم. ويجب أن يكون لكل مخالفة مسؤول ونتيجة قابلة للتتبع.

Q52: بوابات التحقق المستمرة

هل نعتمد أن CI لا يكتفي بالفحص عند Pull Request، بل يعيد تشغيل الفحوص المناسبة عند تحديث الاعتماديات أو أدوات التطوير أو قواعد الحوكمة؟

التوصية: نعم. مع عدم ادعاء أن CI يستطيع إثبات توافق Runtime على جهاز فعلي دون تنفيذ اختبار الجهاز.

أجب بـ«نعم للجميع» أو حدد أرقام الأسئلة التي تريد تعديلها.

-------

الجولة الثامنة: إغلاق القرارات التشغيلية المؤجلة

هذه الجولة تحسم كيفية التعامل مع المعلومات التي لا نملك دليلاً عليها بعد، وكيفية تحويل المبادئ المعتمدة إلى نظام قابل للإدارة. لن أفترض إصدارات أو أجهزة أو أسماء مسؤولين أو أدوات غير مثبتة.

Q53. الإصدارات التي لم يتم التحقق منها

التوصية: لا نعلن إصدار Scriptable أو iOS مدعوماً قبل تحديده والتحقق منه. نسجل القيم المجهولة بوصفها Pending Verification، ولا نخلطها مع Unsupported أو Not Verified.

هل تعتمد ذلك؟

Q54. الأجهزة المستهدفة

التوصية: لا يُعتبر iPhone أو iPad مدعوماً لمجرد أن Scriptable يعمل عليه. نعلن دعم الجهاز بعد إدراجه في مصفوفة الاختبار وتوفير دليل مناسب، ونفصل بين الجهاز المستهدف والجهاز المختبر فعلياً.

هل تعتمد ذلك؟

Q55. تعيين المسؤوليات

التوصية: نحدد المسؤوليات أولاً بأسماء الأدوار، مثل مالك الدستور ومراجع التغيير ومعتمد الاستثناء. تُسند الأسماء الفعلية لاحقاً بعد التحقق من الأشخاص وصلاحياتهم. ويمكن للشخص الواحد شغل أكثر من دور، مع تسجيل ذلك صراحة.

هل تعتمد ذلك؟

Q56. تجديد الاستثناءات

التوصية: لا يُمدد الاستثناء تلقائياً. عند اقتراب تاريخ انتهائه، يُعاد تقديمه ومراجعته واعتماده من جديد، مع تحديث المخاطر والأدلة والضوابط. انتهاء الاستثناء يعني توقف صلاحية الخروج عن القاعدة.

هل تعتمد ذلك؟

Q57. مراجعة الأدلة

التوصية: نعتمد المراجعة القائمة على الأحداث والمخاطر، لا مدة موحدة لكل الأدلة. ومن أمثلة الأحداث التي تستدعي إعادة التحقق: تحديث Scriptable أو iOS، تغيير API، تعديل اعتماد، ظهور دليل متعارض، أو اكتشاف خلل. ويمكن إضافة مدد زمنية لاحقاً للأدلة عالية المخاطر إذا أمكن تبريرها.

هل تعتمد ذلك؟

Q58. مصدر سجل التوافق

التوصية: يكون هناك مصدر بيانات مركزي واحد لسجل التوافق، بصيغة قابلة للقراءة الآلية والتحقق عبر CI، مع إمكانية عرض بياناته في وثائق بشرية مقروءة. لا نحدد اسم الملف أو تنسيقه النهائي قبل مراجعة بنية المشروع المسموح بها.

هل تعتمد ذلك؟

Q59. حدود بوابات CI

التوصية: لا يمر التغيير إلا بعد اجتياز الفحوص الآلية المنطبقة عليه. أما الاختبارات التي تتطلب جهازاً فعلياً أو تشغيل Scriptable، فتسجل كأدلة مستقلة، ولا يجوز لنجاح CI أن يحل محلها أو يدّعي تنفيذها. وإذا كان اختبار مطلوباً ولم يُنفذ، فلا يُسجل على أنه ناجح.

هل تعتمد ذلك؟

أجب بالطريقة المختصرة: «نعم للجميع»، أو اذكر أرقام القرارات التي تريد تعديلها مع التعديل المطلوب.

------------

الجولة التاسعة: بنية الدستور وآلية إدارته

ننتقل الآن من تحديد المبادئ إلى تحديد شكل النظام المعياري نفسه. هذه قرارات تخص التنظيم والعلاقات، وليست أسماء ملفات أو مسارات فعلية.

Q60. طبقات الوثائق

التوصية: تنظيم وثائق الحوكمة في طبقات واضحة:

* الدستور: المبادئ والسلطة والأحكام العليا.
* السياسات: مجموعات القواعد التفصيلية.
* المعايير والإجراءات: كيفية تطبيق القواعد والتحقق منها.
* السجلات: التوافق والأدلة والاستثناءات والقرارات.
* المراجع: المصادر الرسمية والمجتمعية والمراجع الفنية.

تكون الطبقات الأدنى خاضعة للأعلى ولا تستطيع تعديل أحكامها.

Q61. لغة الدستور

التوصية: اعتماد الإنجليزية للمصطلحات المعيارية وأسماء القواعد والحقول التقنية، مع شروح عربية عند الحاجة. تُستخدم المصطلحات MUST وMUST NOT وSHOULD وSHOULD NOT وMAY بمعانيها المعيارية المحددة، دون ترجمة تغيّر قوتها الإلزامية.

Q62. ثبات معرّفات القواعد

التوصية: لكل قاعدة معرّف ثابت لا يتغير عند تغيير عنوانها أو صياغتها. إذا قُسمت قاعدة أو أُلغيت، يحتفظ السجل بتاريخها وعلاقتها بالقواعد البديلة، ولا يعاد استخدام معرّفها لقاعدة أخرى.

Q63. التتبع بين القاعدة والتنفيذ

التوصية: يجب أن يمكن تتبع كل قاعدة إلى:

* المكونات والنطاقات التي تنطبق عليها.
* آلية الإنفاذ المناسبة.
* الفحوص التي تتحقق منها.
* الأدلة والاستثناءات والقرارات المرتبطة بها.

والعكس صحيح: لا يُضاف فحص إلزامي في CI دون مرجع إلى قاعدة أو متطلب حوكمة واضح.

Q64. اقتراح تغيير الدستور

التوصية: يمر كل تغيير معياري بمسار موثق: اقتراح، تحديد الأثر والنطاق، مراجعة، اعتماد، إصدار، ثم تحديث السجلات والوثائق المرتبطة. لا يصبح التغيير نافذاً لمجرد تعديل ملف.

Q65. حالة القواعد

التوصية: لكل قاعدة دورة حياة مستقلة تشمل Proposed وActive وDeprecated وRetired. لا تُحذف القاعدة القديمة من السجل، بل يُحتفظ بتاريخها وسبب تغييرها والبديل إن وجد.

Q66. الفصل بين الوثائق والبيانات

التوصية: تبقى الشروح البشرية في الوثائق، وتبقى سجلات التوافق والأدلة والاستثناءات في بيانات منظمة قابلة للتحقق الآلي. يجب أن تكون هناك روابط ومعرّفات متبادلة بينهما، دون نسخ متضارب للمعلومة نفسها.

Q67. اعتماد إصدار الدستور

التوصية: لا يُنشر إصدار جديد إلا بعد:

* مراجعة التغييرات وتصنيفها وفق Semantic Versioning.
* التحقق من سلامة المعرّفات والروابط.
* التحقق من اكتمال السجلات المتأثرة.
* اجتياز فحوص الحوكمة الآلية.
* تسجيل جهة الاعتماد وتاريخ الإصدار.

هل تعتمد القرارات Q60 إلى Q67 جميعها؟

يمكنك الإجابة بـ «نعم للجميع»، أو ذكر أرقام القرارات التي تريد تعديلها.

----------

الجولة العاشرة: سلامة النظام المعياري ومنع الانحراف

هذه الجولة تختبر ما يحدث عندما تتعارض القواعد أو تتغير البيئة أو تصبح آليات الإنفاذ نفسها غير موثوقة.

Q68. تعارض القواعد

التوصية: عند اكتشاف تعارض بين قاعدتين، لا يختار المؤلف إحداهما بصورة ضمنية. يُسجل التعارض، ويُحدد مصدره ومستوى القاعدتين ونطاقهما، ثم يُحل وفق ترتيب الأولوية المعتمد. وتظل القاعدة الأعلى نافذة حتى اعتماد تعديل رسمي.

Q69. التغييرات ذات الأثر الواسع

التوصية: كل تغيير يؤثر في عدة قواعد أو مكونات أو سياقات تشغيل يتطلب تحليل أثر موثق قبل اعتماده. يشمل التحليل التبعيات، والأدلة المتأثرة، والفحوص المطلوب تحديثها، ومخاطر التراجع عن التغيير.

Q70. سلامة سجل الأدلة

التوصية: لا تُستبدل الأدلة القديمة أو تُمحى عند ظهور أدلة أحدث أو متعارضة. يُحتفظ بالتاريخ، وتُربط الأدلة الجديدة بالقديمة، مع تحديد حالة كل دليل وسبب تغيير تقييم صلاحيته.

Q71. فشل أدوات الإنفاذ

التوصية: إذا تعطل فحص إلزامي أو تعذر تشغيله أو أعاد نتيجة غير موثوقة، فلا يُعامل ذلك كنجاح. تكون النتيجة BLOCKED أو INDETERMINATE بحسب الحالة، ولا يُسمح بتجاوزها إلا عبر مسار استثناء معتمد إن كان ذلك مسموحاً للقاعدة.

Q72. سلامة سلسلة الاعتماديات

التوصية: لا يكفي أن تكون المكتبة متوافقة وظيفياً. يجب تقييم مصدرها وإصدارها وسلامة محتوياتها واعتمادياتها العابرة ومخاطرها الأمنية وترخيصها. ويُعاد التقييم عند تغيير الإصدار أو المصدر أو سلسلة الاعتماديات.

Q73. التراجع عن إصدار معياري

التوصية: يجب أن تكون هناك آلية موثقة لمعالجة إصدار دستوري أو تغييرات معيارية ثبت أنها خاطئة أو أضرت بالمشروع. لا يُمحى الإصدار المنشور؛ بل يصدر تصحيح أو إصدار لاحق، مع توثيق أثر التراجع والقرارات المتأثرة.

Q74. اكتشاف انحراف الوثائق عن التنفيذ

التوصية: تُعامل الوثائق والقواعد والفحوص والسلوك الفعلي باعتبارها عناصر يجب أن تبقى متسقة. عند اكتشاف انحراف، يُفتح سجل مخالفة، ويُحدد هل الخلل في التنفيذ أو القاعدة أو الاختبار أو التوثيق، ثم يُعالج ويُتحقق منه قبل الإغلاق.

Q75. مراجعة صلاحية الدستور ككل

التوصية: إلى جانب مراجعة القواعد والأدلة منفردة، تُجرى مراجعة شاملة عند التغييرات الكبرى في Scriptable أو JavaScriptCore أو iOS أو بنية المشروع أو نموذج التهديد الأمني. الغرض التأكد من أن الدستور ما زال صالحاً، لا مجرد أن كل قاعدة منفردة تبدو سليمة.

هل تعتمد Q68 إلى Q75 جميعها؟

أجب بـ «نعم للجميع»، أو اذكر أرقام القرارات التي تريد تعديلها.
