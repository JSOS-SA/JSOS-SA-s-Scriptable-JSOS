المواصفات الموحدة لمشروع Scriptable

Unified Scriptable Engineering Constitution & Technical Standards

الحالة: مسودة موحدة للمراجعة والاعتماد
الإصدار المقترح: 1.0.0
نطاق الأجهزة: iPhone فقط
نموذج المسؤولية: مطور ومسؤول واحد
الأساس: قرارات Q1–Q75، ومستند قواعد ومعايير تطبيق Scriptable ولغة JavaScript وبيئة تشغيلها.

⸻

1. الغرض والنطاق

تهدف هذه المواصفات إلى إنشاء مرجع هندسي موحد يحكم تطوير ومراجعة واختبار وصيانة مشاريع Scriptable.

وتشمل المواصفات:

* لغة JavaScript ومعيار ECMAScript.
* محرك Apple JavaScriptCore.
* واجهات Scriptable الأصلية.
* نظام الوحدات والاستيراد.
* Scriptable Main Runtime.
* WebView Runtime.
* TypeScript وتعريفاته.
* بنية المشروع والمعمارية.
* المكتبات والاعتماديات.
* جودة الشيفرة والبيانات.
* الأمان والخصوصية.
* الأداء وإدارة الموارد.
* الاختبارات والتحقق من التوافق.
* إدارة التغييرات والاستثناءات.
* الحوكمة وسجلات الأدلة.
* التكامل مع GitHub وCI.

هذه المواصفات تحكم العمل الهندسي، ولا تعني أن كل واجهة أو سياق أو ميزة مدعوم تلقائياً.

2. حدود المشروع والمسؤوليات

2.1 الأجهزة المستهدفة

1. MUST أن يكون iPhone هو الجهاز المستهدف الوحيد.
2. MUST NOT اعتبار iPad جهازاً مستهدفاً.
3. MUST NOT توسيع نطاق الدعم إلى أي جهاز آخر دون تعديل رسمي للمواصفات.
4. MUST عدم تعميم نتيجة اختبار جهاز على جهاز آخر.
5. MUST تسجيل طراز iPhone وإصدار iOS وإصدار Scriptable عند توثيق اختبارات التوافق.
6. MUST عدم إعلان دعم إصدار أو جهاز قبل وجود دليل اختبار مناسب.

2.2 نموذج المسؤولية

يتولى شخص واحد جميع مسؤوليات المشروع، بما فيها:

* ملكية المواصفات والدستور.
* كتابة الشيفرة وتطويرها.
* مراجعة التغييرات.
* الاختبارات والتحقق.
* اعتماد التغييرات والاستثناءات.
* إدارة الإصدارات.
* النشر والصيانة.
* إدارة سجلات الأدلة والتوافق والمخاطر.

يمكن فصل هذه المسؤوليات مفاهيمياً في الإجراءات والسجلات، لكن لا يجوز افتراض وجود أشخاص مختلفين لشغلها.

2.3 مبدأ المسؤولية

MUST أن تكون كل موافقة أو مراجعة أو نتيجة اختبار أو عملية نشر قابلة للإسناد إلى المسؤول الوحيد، مع تسجيل التاريخ والنتيجة والدليل المناسب.

3. النموذج التقني وطبقات بيئة التشغيل

يجب التمييز بين الطبقات التالية وعدم التعامل معها باعتبارها بيئة واحدة:

الطبقة	المسؤولية
JavaScript	لغة البرمجة
ECMAScript	المعيار الذي يحدد قواعد اللغة وسلوكها
JavaScriptCore	محرك تنفيذ JavaScript
Scriptable	التطبيق المضيف وواجهاته الأصلية
Main Runtime	سياق تشغيل السكربت الأساسي
WebView Runtime	سياق صفحة الويب
TypeScript	فحص الأنواع وأدوات التطوير
Apple Native APIs	واجهات Apple الأصلية، ولا تثبت إتاحتها المباشرة داخل Scriptable

3.1 قاعدة الفصل بين الطبقات

1. وجود خاصية في ECMAScript لا يثبت وجودها في كل بيئة تشغيل.
2. وجود واجهة في JavaScriptCore لا يثبت أنها متاحة مباشرة للسكريبت.
3. وجود تعريف في TypeScript لا ينشئ واجهة Runtime.
4. نجاح الشيفرة في Node.js لا يثبت توافقها مع Scriptable.
5. نجاح الشيفرة في WebView لا يثبت توافقها مع Main Runtime.
6. MUST تحديد الطبقة والسياق قبل اعتماد أي واجهة أو ميزة.

4. معيار JavaScript وECMAScript

4.1 خط الأساس

1. MUST اعتماد ECMAScript 2015 (ES6) خط أساس موثق للمشروع.
2. MUST عدم اعتماد ميزات أحدث تلقائياً.
3. MUST التحقق من الميزات الأحدث باختبار فعلي داخل Scriptable.
4. MUST فصل توافق صياغة اللغة عن توافق الكائنات والوظائف القياسية.
5. MUST عدم اعتبار نجاح الترجمة أو الفحص الثابت دليلاً على التوافق التشغيلي.

4.2 الميزات الحديثة

أي ميزة لم يثبت توافقها مع خط الأساس أو الجهاز المستهدف تعامل باعتبارها غير متحققة حتى يتم اختبارها.

ويشمل ذلك، على سبيل المثال، الميزات التي ظهرت بعد ES2015 مثل async/await وBigInt وميزات المصفوفات الحديثة.

لا يُسمح بافتراض دعمها لمجرد وجودها في إصدار حديث من JavaScriptCore أو في TypeScript.

4.3 جودة الشيفرة

MUST:

* استخدام const وlet في الشيفرة الجديدة وفق الحاجة.
* تجنب var ما لم توجد ضرورة واضحة.
* استخدام المقارنات الصريحة.
* التعامل مع null وundefined بوضوح.
* معالجة الأخطاء المتوقعة.
* تجنب الدوال الضخمة والمسؤوليات المتعددة.
* تقليل التكرار.
* استخدام أسماء واضحة.
* تجنب القيم والنصوص السحرية.
* توثيق المنطق المعقد وسبب وجوده.
* فصل منطق الأعمال عن الوصول إلى النظام قدر الإمكان.

5. واجهات Scriptable الأصلية

5.1 مصدر الحقيقة

توثيق Scriptable الرسمي هو المرجع الأساسي لإثبات واجهات التطبيق.

قبل استخدام أي API، MUST التحقق من:

1. وجود الواجهة في التوثيق الرسمي.
2. اسم الواجهة الصحيح.
3. أسماء الخصائص والدوال.
4. أنواع المعاملات.
5. القيمة المعادة.
6. السلوك غير المتزامن عند وجوده.
7. القيود والتحذيرات والخصائص المهملة.
8. سياق التشغيل الذي تستخدم فيه.
9. القيود المرتبطة بإصدار Scriptable وiOS.

5.2 عائلات الواجهات

تشمل العائلات التي ينبغي تنظيمها ومراجعتها:

* التشغيل والمدخلات والمخرجات: args وconfig وScript.
* الملفات والتخزين: FileManager وKeychain وData وPath.
* الشبكات: Request.
* خدمات الجهاز: Device وLocation وPhotos وContacts.
* التقويم والتذكيرات: Calendar وCalendarEvent وReminder.
* واجهات المستخدم: Alert وDatePicker وTextField وUITable.
* الويب: WebView وSafari.
* الأدوات المصغرة: ListWidget ومكوناته.
* الرسم والصور: DrawContext وImage وColor وFont.
* التاريخ والصوت والرسائل والتحليل: DateFormatter وSpeech وMail وXMLParser وغيرها.

هذه أسماء عائلات للتنظيم، وليست إثباتاً مستقلاً لكل خاصية أو دالة داخلها.

5.3 حظر الافتراض

MUST NOT:

* اختراع واجهات أو خصائص غير موثقة.
* الاعتماد على أمثلة الإنترنت دون التحقق.
* افتراض أن كل واجهات Apple متاحة مباشرة.
* افتراض أن كل مكتبات npm تعمل داخل Scriptable.
* استخدام تعريف TypeScript وحده لإثبات وجود API.

6. نظام الوحدات والاستيراد

6.1 آلية Scriptable

يعتمد نظام الوحدات على:

* importModule()
* module.exports

ويجب الالتزام بالسلوك الموثق للاستيراد وتحديد مسارات الملفات بصورة صحيحة.

6.2 حدود التوافق مع Node.js

وجود importModule وmodule.exports لا يعني وجود نظام Node.js كاملاً.

MUST NOT افتراض توفر:

* require()
* process
* node_modules
* واجهات Node.js الأصلية
* جميع مكتبات npm
* نظام ES Modules كما في Node.js أو المتصفح.

6.3 مسؤولية الوحدة

كل وحدة MUST أن يكون لها غرض واضح ومدخلات ومخرجات وعقد مفهوم.

MUST تجنب:

* تكرار المنطق.
* الاعتماد الدائري.
* الترابط غير الضروري.
* تعدد المسؤوليات داخل الوحدة.
* الاعتماد المباشر على واجهات النظام عندما يمكن فصل منطق الأعمال عنها.

7. الفصل بين Main Runtime وWebView

7.1 Main Runtime

هو سياق تشغيل السكربت الأساسي في Scriptable.

يمكن التعامل فيه مع واجهات التطبيق الموثقة، مثل FileManager وRequest وKeychain وScript وargs.

MUST NOT افتراض وجود document أو window أو DOM فيه.

7.2 WebView Runtime

هو سياق صفحة ويب مستقل داخل WebView.

يمكن أن يحتوي على HTML وCSS وJavaScript وDOM وdocument وفق بيئة صفحة الويب.

يجب استخدام واجهات WebView الموثقة للتحكم في الصفحة، مثل evaluateJavaScript() وgetHTML() وwaitForLoad() وعمليات التحميل والعرض.

7.3 قواعد الفصل

1. MUST تحديد مكان تنفيذ كل شيفرة: Main Runtime أو WebView.
2. MUST عدم نقل افتراضات DOM إلى Main Runtime.
3. MUST عدم اعتبار WebView بديلاً عن FileManager.
4. MUST اختبار JavaScript داخل WebView بصورة مستقلة عن السكربت الأساسي.
5. MUST التعامل مع التواصل بين السياقين بوضوح والتحقق من البيانات المنقولة.
6. MUST مراعاة سلوك العمليات غير المتزامنة وأخطاء التحميل.

8. TypeScript وتعريفات Scriptable

8.1 الدور

TypeScript أداة تطوير وفحص ثابت، وليس بيئة تشغيل أصلية داخل Scriptable.

8.2 تعريفات الأنواع

يمكن الاستفادة من @types/scriptable-ios وDefinitelyTyped ومشاريع توليد التعريفات، لكن يجب التعامل معها باعتبارها مراجع مساعدة غير رسمية.

MUST مقارنة التعريفات مع توثيق Scriptable الرسمي.

MUST تسجيل التعريفات:

* الصحيحة.
* الناقصة.
* الزائدة.
* المتعارضة.
* غير المتحققة.

8.3 إعدادات الفحص

يجب ضبط target وlib وtypes بما يتناسب مع بيئة التشغيل المستهدفة.

يجب عدم تحميل تعريفات DOM تلقائياً إلى فحص Main Runtime إذا كانت ستسمح باستخدام واجهات غير موجودة فيه.

يجب التمييز بين:

* TypeScript Declaration.
* JavaScript Output.
* Runtime API.

نجاح فحص الأنواع لا يثبت وجود الواجهة وقت التشغيل.

8.4 دورة TypeScript

عند استخدام TypeScript:

1. كتابة ملفات المصدر.
2. فحص الأنواع.
3. تحويل أو بناء JavaScript عند الحاجة.
4. التحقق من توافق الناتج مع Scriptable.
5. تشغيل الناتج داخل التطبيق.
6. تسجيل النتيجة والدليل.

9. المكتبات والاعتماديات

9.1 السياسة الافتراضية

MUST منع إضافة المكتبات الخارجية افتراضياً.

أي مكتبة جديدة تحتاج إلى مراجعة قبل اعتمادها.

9.2 عناصر المراجعة

يجب فحص:

* المصدر وموثوقيته.
* الترخيص.
* الإصدار.
* الاعتماديات المباشرة وغير المباشرة.
* التوافق مع Scriptable.
* الاعتماد على Node.js أو DOM أو Browser APIs.
* نظام الوحدات المستخدم.
* الأداء واستهلاك الذاكرة.
* المخاطر الأمنية.
* إمكانية الصيانة والتحديث.

9.3 شرط القبول

نجاح التثبيت أو التجميع أو الفحص لا يثبت توافق المكتبة مع Runtime.

لا تعتمد المكتبة قبل إثبات توافقها في السياق المستهدف أو توثيق أنها غير متحققة مع منع الاعتماد عليها تشغيلياً.

10. المعمارية وتنظيم المشروع

10.1 المبادئ

MUST اعتماد بنية واضحة قابلة للصيانة والاختبار.

MUST فصل المسؤوليات ومنع التكرار وتقليل الترابط والاعتماد الدائري.

10.2 الطبقات المعمارية

الطبقة	المسؤولية
Core	الإعدادات والثوابت والأخطاء والتسجيل
Services	الشبكة والتخزين والمصادقة والخدمات الخارجية
Data	التحقق والتحويل والعقود والمخططات
Features	منطق الأعمال ووظائف المستخدم
UI	القوائم والجداول والواجهات والأدوات المصغرة
Scriptable Host APIs	التكامل مع واجهات Scriptable
Tests	اختبارات المنطق والعقود وRuntime

هذا تقسيم معماري مرجعي، وليس هيكلاً إلزامياً ثابتاً لكل مشروع صغير.

10.3 عقود الوحدات

كل وحدة عامة MUST توضح:

* مسؤوليتها.
* مدخلاتها.
* مخرجاتها.
* الأخطاء المحتملة.
* اعتمادياتها.
* الواجهات التي تعرضها للوحدات الأخرى.

11. جودة البيانات ومعالجة الأخطاء

11.1 البيانات

كل بيانات تأتي من الشبكة أو الملفات أو المستخدم أو سياق التشغيل تعتبر بيانات تحتاج إلى تحقق.

MUST:

* التحقق من البنية المتوقعة.
* التحقق من القيم المطلوبة.
* التعامل الصريح مع القيم المفقودة.
* التمييز بين null وundefined.
* التحقق من الأنواع والنطاقات.
* عدم اعتبار نجاح التحميل دليلاً على صحة البيانات.

11.2 الأخطاء

MUST:

* التعامل مع الأخطاء المتوقعة باستخدام try/catch.
* معالجة رفض Promise.
* تسجيل معلومات تشخيصية مفيدة.
* عدم إخفاء الأخطاء بصمت.
* وضع سياسة لإعادة المحاولة.
* منع إعادة العمليات التي قد تنتج بيانات أو معاملات مكررة دون حماية مناسبة.

يجب أن تظل حالة النظام واضحة عند الفشل، وألا يتحول الفشل إلى نتيجة نجاح وهمية.

12. الأمان والخصوصية والموثوقية

12.1 الأسرار

MUST تخزين كلمات المرور والرموز والمفاتيح الحساسة في Keychain عند ملاءمة ذلك.

MUST NOT تضمين الأسرار داخل ملفات JavaScript أو طباعتها في السجلات.

12.2 الشبكة

MUST:

* استخدام HTTPS.
* التحقق من الاستجابات.
* تحديد مهلات مناسبة.
* معالجة انقطاع الاتصال.
* الحفاظ على التحقق من شهادات HTTPS.

MUST NOT تعطيل التحقق من الشهادات دون مبرر محدد وموثق.

12.3 الملفات

MUST التحقق من المسارات والوجهات قبل العمليات الحساسة.

MUST الانتباه إلى سلوكيات iCloud، وإمكانية الحاجة إلى تنزيل الملف قبل القراءة.

MUST الاحتفاظ بنسخ احتياطية عند الحاجة، خصوصاً قبل الحذف أو النقل أو الاستبدال.

12.4 الخصوصية

يجب طلب أقل قدر لازم من الصلاحيات للوصول إلى الموقع والصور وجهات الاتصال والتقويم.

يجب التعامل مع رفض الإذن بصورة واضحة دون افتراض نجاح العملية.

12.5 الشيفرة الخارجية

MUST NOT تشغيل شيفرة خارجية غير موثوقة باستخدام eval أو أي وسيلة تنفيذ ديناميكي غير آمنة.

13. الأداء وإدارة الموارد

MUST:

* تقليل عمليات القراءة والكتابة المتكررة.
* تجنب تحميل الملفات والصور الكبيرة دون حاجة.
* تحديد مهلات الشبكة.
* مراعاة قيود الذاكرة في Widgets.
* تجنب العمليات الثقيلة في سياقات قصيرة العمر.
* استخدام التخزين المؤقت عند ملاءمته.
* عدم افتراض أن Widget سيتحدث فور طلب التحديث.

يجب تقييم الأداء وفق السياق الفعلي، وليس وفق تشغيل السكربت داخل التطبيق فقط.

14. سياقات التشغيل المستهدفة

تختلف قيود التشغيل باختلاف السياق.

السياقات التي يمكن أن يشملها المشروع، وفق الحاجة، هي:

* التشغيل المباشر داخل Scriptable.
* Widget.
* Shortcuts وSiri.
* Share Sheet.
* URL Scheme.
* WebView.

هذه السياقات لا تعني توسيع نطاق الأجهزة؛ فكل الاختبارات المستهدفة تظل على iPhone فقط.

MUST اختبار كل سياق مطلوب بصورة مستقلة.

MUST عدم اعتبار نجاح السكربت داخل التطبيق دليلاً على نجاحه في Widget أو Shortcuts أو Share Sheet أو WebView.

15. الاختبارات والتحقق من التوافق

15.1 طبقات الاختبار

يجب اعتماد طبقات تحقق منفصلة:

1. Syntax: صحة الصياغة.
2. Static Analysis: تحليل الشيفرة واكتشاف المشكلات.
3. Type Checking: فحص الأنواع.
4. Unit Testing: اختبار منطق الوحدات.
5. Integration Testing: اختبار تكامل الخدمات والواجهات.
6. API Compatibility: التحقق من واجهات Scriptable.
7. Runtime Verification: التشغيل الفعلي داخل Scriptable.
8. Context Verification: اختبار سياق التشغيل المقصود.
9. Security Testing: فحص الأمان والمخاطر.

15.2 حدود الأدوات

* ESLint لا يثبت وجود API أصلية.
* TypeScript لا ينشئ واجهات Runtime.
* Test262 لا يختبر واجهات Scriptable الأصلية.
* نجاح Node.js لا يثبت توافق Scriptable.
* نجاح البناء لا يثبت نجاح التشغيل على iPhone.
* نجاح الفحص الثابت لا يعوض اختبار التطبيق الفعلي.

15.3 أدوات الفحص

يمكن استخدام:

* TypeScript Compiler.
* ESLint.
* Prettier.
* Test262.
* Fallow.
* اختبارات Scriptable الفعلية على الجهاز.

يجب اختيار الأداة وفق نوع التحقق المطلوب، وعدم منحها صلاحية إثبات ما لا تختبره.

15.4 مصفوفة التوافق

يجب أن يسجل كل اختبار:

* اسم API أو الميزة.
* إصدار Scriptable.
* إصدار iOS.
* طراز iPhone.
* سياق التشغيل.
* نتيجة الاختبار.
* تاريخ الاختبار.
* رابط التوثيق.
* الدليل الفعلي.
* الملاحظات والقيود.

15.5 حالات التوافق

يجب التمييز بين الحالات التالية:

* موثق.
* مختبر.
* متوافق.
* غير متوافق.
* غير متحقق.

لا تستخدم عبارة «متوافق بالكامل» دون تحديد النطاق وإثبات الاختبارات المطلوبة.

15.6 إثبات ميزة JavaScript

عند اعتماد ميزة جديدة:

1. تحديد الميزة ومعيارها.
2. تحديد إصدار ECMAScript الذي أضافها.
3. التحقق من الأدلة المتاحة للمحرك.
4. كتابة اختبار مستقل.
5. تشغيل الاختبار داخل Scriptable على iPhone المستهدف.
6. تسجيل النتيجة والإصدارات والتاريخ.

نتيجة الاختبار تثبت السلوك في البيئة التي نُفذ فيها فقط.

16. الحوكمة والقواعد المعيارية

16.1 ترتيب المرجعيات

يجب اعتماد التسلسل التالي:

1. الدستور والمواصفات المعتمدة للمشروع.
2. السياسات والإجراءات والمعايير التابعة لها.
3. توثيق Scriptable الرسمي عند تحديد واجهات التطبيق.
4. وثائق Apple JavaScriptCore عند تحديد سلوك المحرك.
5. ECMAScript عند تحديد قواعد اللغة.
6. وثائق TypeScript عند تحديد سلوك أدوات التطوير.
7. تعريفات المجتمع والمستودعات والأمثلة بوصفها مراجع مساعدة.
8. الاختبار الفعلي لإثبات السلوك في بيئة التشغيل المستهدفة.

لا يجوز لمصدر أدنى مرتبة إلغاء قاعدة أعلى منه.

16.2 صياغة الإلزام

تستخدم المصطلحات التالية:

* MUST: إلزامي.
* MUST NOT: محظور.
* SHOULD: موصى به.
* SHOULD NOT: لا يوصى به.
* MAY: اختياري.

16.3 مستويات الإنفاذ

* BLOCK: يمنع اعتماد التغيير أو دمجه.
* WARN: يسمح بالاستمرار مع تسجيل التحذير.
* GUIDE: توجيه هندسي غير مانع.

16.4 تعريف القاعدة

كل قاعدة معيارية يجب أن تتضمن:

* معرّفاً ثابتاً.
* الاسم.
* النص الإلزامي.
* النطاق.
* المبرر.
* المصدر المرجعي.
* طريقة التحقق.
* مستوى الإنفاذ.
* شروط الاستثناء.

MUST عدم إعادة استخدام معرّفات القواعد القديمة بعد إيقافها.

17. الاستثناءات والمخاطر والمخالفات

17.1 الاستثناء

الاستثناء ليس وسيلة لتجاوز القواعد دون توثيق.

يجب أن يتضمن:

* القاعدة المستثناة.
* سبب الاستثناء.
* نطاقه.
* المخاطر.
* الضوابط البديلة.
* تاريخ البداية والانتهاء.
* المسؤول عن اعتماده.

لا يسمح باستثناء مفتوح المدة.

17.2 دورة حياة الاستثناء

Proposed → Reviewed → Approved → Active → Expired / Revoked

17.3 تقييم المخاطر

يجب تقييم:

* احتمال الفشل.
* شدة الأثر.
* صعوبة اكتشاف الفشل.

17.4 دورة حياة المخالفة

Detected → Classified → Assigned → Remediated / Exception Requested → Verified → Closed

يجب تسجيل المخالفات والأدلة والإجراءات التصحيحية، وعدم إغلاق المخالفة قبل التحقق من المعالجة.

18. GitHub وCI وإدارة التغييرات

18.1 الفحوص الآلية

تستخدم GitHub Actions لتشغيل الفحوص المناسبة للمشروع.

يجب أن تشمل الفحوص بحسب نطاق المشروع:

* Syntax.
* Static Analysis.
* Type Checking.
* فحوص الاعتماديات.
* فحوص الأسرار والأمان.
* فحوص قواعد الحوكمة.
* اختبارات المنطق والعقود.

18.2 حماية الفرع الرئيسي

يجب حماية الفرع الرئيسي، واعتماد Pull Requests والفحوص المطلوبة قبل الدمج.

لا يسمح بالدمج عند فشل فحص إلزامي.

تعطل أداة الفحص لا يعني نجاح الفحص؛ يجب تسجيل الحالة باعتبارها BLOCKED أو INDETERMINATE بحسب السبب.

18.3 إدارة التغييرات المعيارية

أي تعديل على المواصفات يمر بمراحل:

1. اقتراح التغيير.
2. تحليل الأثر.
3. المراجعة.
4. الاعتماد.
5. تحديث الإصدار.
6. حفظ سجل القرار والدليل.

18.4 الإصدارات

تعتمد Semantic Versioning:

* Major: تغيير غير متوافق أو إعادة هيكلة معيارية جوهرية.
* Minor: إضافة متوافقة لقواعد أو متطلبات جديدة.
* Patch: تصحيح لا يغير المعنى المعياري الأساسي.

يجب الاحتفاظ بتاريخ الإصدارات والقرارات والأدلة القديمة.

يجب إثبات أربعة أمور مستقلة:

3. Context Compatibility: عملها في سياق التشغيل المقصود.
4. Device Verification: نجاح اختبارها على iPhone وإصدار Scriptable وiOS المستهدفين.

أي نقطة لا يتوفر عليها دليل كافٍ تسجل باعتبارها غير متحققة، ولا يجوز تحويلها إلى حقيقة معتمدة بالتخمين.

25. قواعد استخدام قائمة المراجع

1. MUST إظهار عنوان URL كاملاً في وثائق المشروع، ويبدأ بـ https:// عندما يكون الرابط آمناً عبر HTTPS.
2. MUST عدم استبدال الرابط باسم مختصر أو رابط مخفي.
3. MUST الرجوع إلى Scriptable Official Documentation أولاً عند فحص واجهات التطبيق.
4. MUST الرجوع إلى Apple JavaScriptCore لفهم المحرك، دون الخلط بين واجهاته وواجهات Scriptable.
5. MUST الرجوع إلى ECMAScript لتحديد قواعد اللغة.
6. MUST الرجوع إلى TypeScript Official Documentation لتحديد سلوك أدوات الفحص والتحويل.
7. MUST التعامل مع تعريفات DefinitelyTyped ومشاريع التوليد باعتبارها مراجع مساعدة وليست مصادر رسمية لواجهات Runtime.
8. MUST تسجيل المصدر المحدد الذي استندت إليه كل قاعدة أو نتيجة توافق.
9. MUST عدم اعتبار وجود رابط في هذه القائمة دليلاً على أن محتواه يثبت دعماً معيناً.
10. MUST إعادة التحقق من الروابط والمحتوى عند تحديث المواصفات أو إجراء مراجعة توافق.
